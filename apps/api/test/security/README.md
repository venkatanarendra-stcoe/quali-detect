# Security regression suite

Run: `pnpm test:security` (from the repo root). Decision and scope: `docs/decisions/ADR-008-SECURITY-REGRESSION-SUITE.md`.

It covers **only** tenant isolation, the 404/403 authorization rule, platform/tenant session separation, segregation of duties and the sign-in/MFA throttling of ADR-010: 441 checks, 17 controls and 1 integrity test. It is a black box over HTTP, so it works against any implementation of the API (Fastify today, Express after ADR-007).

## What it needs

- PostgreSQL server binaries (`initdb`, `pg_ctl`): found through `PG_BIN_DIR`, `/usr/lib/postgresql/*/bin` or `PATH`. The runner starts an **ephemeral** cluster on a free port in a temporary directory and deletes it afterwards. No Docker.
- or `SECURITY_TEST_DATABASE_URL`: an existing, empty, **disposable** database. The runner refuses a database whose name does not contain "test" and never prints the URL.
- Nothing else: no Redis, no RabbitMQ, no `.env` files. Passwords and the MFA code are random for each run.

Development aid: `SECURITY_SUITE_ONLY="PIP-" node apps/api/scripts/security-suite.js` runs only the checks whose name matches (the integrity test is skipped unless it matches too). A filtered run never replaces the full `pnpm test:security`, which is the gate.

Exit codes of the runner (`node apps/api/scripts/security-suite.js`): `0` passed, `1` a check failed (the last API log lines are printed), `2` the environment is unusable (the message says why). Through `pnpm test:security`, pnpm reports `1` for any non-zero exit, so read the message to tell the two apart.

## Files

- `../../scripts/security-suite.js`: provisions the database, migrates and seeds, starts the API, runs the tests, tears everything down.
- `security.test.js`: the checks (data-driven, grouped) plus controls and the integrity test. The SCM groups run partly in-process: the scm worker's handlers (reconciler, state transitions, event consumer for `installation.deleted`) and the notification handler, against the disposable database and the stub.
- `helpers/http.js`: minimal `fetch` client with manual cookie handling.
- `helpers/world.js`: builds tenant B and all sessions through the public API.
- `helpers/github-stub.js`: the local GitHub stand-in (plain HTTP, no network) the SCM checks link against; the runner also sets `SCM_LINK_STATE_TTL_SECONDS=3` so `SCM-033` can prove that an expired linking state is refused.
- `helpers/pipeline-db.js`: database integrity of the Pipelines + Triggers tables (`PIPDB-*`, in process): two tenants with two workspaces and repositories each, row factories, and 14 table-driven checks (composite foreign keys, unique identities, immutability triggers, CHECK constraints, RESTRICT), each with a control.
- The Pipeline API checks (`PIP-*`, SPEC pipelines-triggers §14.1, part C) live in `security.test.js` (section 13) and run over HTTP: the world (`pipWorld`, `capWorld`) is built through the public API (GitHub stub, linking and connecting, per-role sessions of the seeded demo tenant, a second tenant) and read back from the disposable database. `capWorld` is a fresh tenant with `pipelines.max` = 2 and `scans.monthly` = 1 for the limit checks and, last, the suspension check.
- The router checks (`PIP-005..008`, `PIP-015..017`, `PIP-028`, `PIP-035..039`, SPEC pipelines-triggers §6.2, part D) live in `security.test.js` (section 14). They deliver SIGNED webhooks through the running API and hand the stored `scm.*.received` envelope to the router IN PROCESS (`createPipelineTriggerHandler` behind the ownership verifier, as the `pipeline-triggers` consumer does), against the disposable database; the world (`rtWorld`) is built through the public API: tenant R with two workspaces, tenant X connecting the same GitHub repository id, tenant Q with one scan per month. No broker is used.
- The schedule checks (`PIP-012`, `PIP-013`, `PIP-040..050`, SPEC pipelines-triggers §5.6, §6.4, part E and its 2026-11-13 fixes: `PIP-048` schedule decision rows, `PIP-049` per-slot jitter, `PIP-050` fall-back days through the handler) live in `security.test.js` (section 15). The scheduler's due-schedule handler (`createScheduleHandler`) runs IN PROCESS against the disposable database with a fixed clock (2026 instants, before the real date, so the planned times the API computes are never due); pipelines are created through the public API, the due state is set in the database, and every check parks the other fixture schedules first. The world (`schWorld`) has tenant S (two workspaces), tenant X (the same GitHub repository id and cron) and tenant Q (one scan per month). `helpers/schedule-fixtures.js` holds the deterministic DST fixtures (Europe/Berlin and America/New_York, both 2026 transitions, fixed instants) as table data for `PIP-043`, `PIP-044` and `PIP-050` (also the whole-day fire counts of the fall-back days and the jitter fixtures); there is no separate feature-test suite.
- `helpers/direct-repos.js`: data-access isolation (`DAL-*`): builds four tenants directly in the database (X owns the data, including one pipeline with a version, a trigger, a queued and a running execution and a trigger decision, Y is the "wrong" tenant, Z holds the uninstall fan-out and notification fixtures, V two workspaces with revoked repositories for the shared restore functions of `@qmentisai/db`) and calls every tenant-scoped repository function in process with another tenant's id (table-driven, one check per function; `DAL-154..187` are the pipelines module and the pipeline scope resolver and ownership check, `DAL-188..198` the trigger router's worker-side repository (`apps/workers/src/pipeline/repository.js`), `DAL-199..207` the schedule handler's (`apps/workers/src/scheduler/schedule-repository.js`; its two platform scans have no tenant argument by design); includes the workspace-link, allow-list and tenant-setting functions, the uninstall/suspension fan-out of the scm worker and the notification recipient lookup).

## Rules

- A new tenant-owned route family adds checks here in the same work item (cross-tenant 404, hidden-workspace 404 vs 403 where relevant, and a control that the legitimate request works).
- The number of checks is asserted (441: the original 68, 9 `THR` throttling checks of ADR-010, 6 `RST` tenant-restore checks, 9 `SEC` secret-storage checks of ADR-009, 21 HTTP-edge checks `AUD`, `IDM`, `ENT`, `COR`, `RATE`, 58 `SCM` checks for the workspace-level GitHub integration and repositories (SPEC §18.3: linking permissions, second workspace, state binding and expiry, tenant setting, workspace isolation, allow-list, unlink, uninstall fan-out and notification, restore on link, the "use an existing installation" discovery and restore on gaining access), run against a local GitHub stub, 207 `DAL` data-access isolation checks, 15 `PIPDB` database-integrity checks of the pipeline tables, 22 `PIP` Pipeline API checks, 13 router checks (part D) and 13 schedule checks (part E)). Changing it means updating ADR-008.
- Never weaken a check to make it pass; never point the suite at a real database.
