# Security regression suite

Run: `pnpm test:security` (from the repo root). Decision and scope: `docs/decisions/ADR-008-SECURITY-REGRESSION-SUITE.md`.

It covers **only** (ADR-008 areas 1 to 17; area 17, added by the owner in part I of the Executions plan, is execution lifecycle integrity, worker credential isolation, realtime authorization, the log and artifact stores and execution API scoping and pagination) tenant isolation, the 404/403 authorization rule, platform/tenant session separation, segregation of duties and the sign-in/MFA throttling of ADR-010 (plus, from the execution module, worker ownership and claim re-validation, credential absence, lease fencing and the stale-queue guarantee, and from part D cancellation and retry: another tenant's execution is a 404, quota released exactly once, a retry never bypasses a gate, a quota or the trust of a fork): 598 checks, 18 controls and 1 integrity test. It is a black box over HTTP, so it works against any implementation of the API (Fastify today, Express after ADR-007).

## What it needs

- PostgreSQL server binaries (`initdb`, `pg_ctl`): found through `PG_BIN_DIR`, `/usr/lib/postgresql/*/bin` or `PATH`. The runner starts an **ephemeral** cluster on a free port in a temporary directory and deletes it afterwards. No Docker.
- or `SECURITY_TEST_DATABASE_URL`: an existing, empty, **disposable** database. The runner refuses a database whose name does not contain "test" and never prints the URL.
- Nothing else: no Redis, no RabbitMQ, no `.env` files. Passwords and the MFA code are random for each run.

Development aid: `SECURITY_SUITE_ONLY="PIP-" node apps/api/scripts/security-suite.js` runs only the checks whose name matches (the integrity test is skipped unless it matches too). A filtered run never replaces the full `pnpm test:security`, which is the gate.

Exit codes of the runner (`node apps/api/scripts/security-suite.js`): `0` passed, `1` a check failed (the last API log lines are printed), `2` the environment is unusable (the message says why). Through `pnpm test:security`, pnpm reports `1` for any non-zero exit, so read the message to tell the two apart.

## Files

- `../../scripts/security-suite.js`: provisions the database, migrates and seeds, starts the API, runs the tests, tears everything down.
- `security.test.js`: the checks (data-driven, grouped) plus controls and the integrity test. The SCM groups run partly in-process: the scm worker's handlers (reconciler, state transitions, event consumer for `installation.deleted`) and the notification handler, against the disposable database and the stub.
- `helpers/http.js`: minimal `fetch` client with manual cookie handling.
- `helpers/world.js`: builds tenant B and all sessions through the public API.
- `helpers/github-stub.js`: the local GitHub stand-in (plain HTTP, no network) the SCM checks link against; the runner also sets `SCM_LINK_STATE_TTL_SECONDS=3` so `SCM-033` can prove that an expired linking state is refused.
- `helpers/repo-state.js`: idempotent repository and installation state transitions (`SCM-063..068`, SPEC repositories-github §16.3 item 7) and the installation-wide reconcile (`SCM-069..072`, item 1c: selection change, webhook producer with per-link-per-minute dedupe over a signed delivery, tenant isolation, partial knowledge): tenants T and U created directly in the database, the scm worker's event consumer, sync job and state functions race each other IN PROCESS with `Promise.all` (event path against sync path, two failures at the threshold, replays, a foreign tenant id, success after unavailable, repeated revoke/suspend/unsuspend), each with a control.
- `helpers/broker-topology.js`: broker topology and publish safety (`BRK-001..004`, SPEC repositories-github §16.3 item 6): the REAL publisher, outbox relay, consumer and outbox repository (against the disposable database) run in process against `FakeBroker`, a channel double with exchanges, queues, direct/topic bindings, confirms and `basic.return` for unroutable mandatory publishes. No real RabbitMQ is touched.
- `helpers/overview-checks.js`: the `OVR-*` checks of `GET /overview` and the Admin-only `dashboard.view` (see Rules below), including the navigation evaluated by `@qmentisai/shared` from the real `GET /me` permissions of a user holding each built-in role at tenant scope.
- `helpers/user-preferences.js`: the `PREF-*` checks of `GET`/`PUT /me/preferences` (SPEC user-preferences §14): forged body/query/header identifiers, two users of one tenant, two tenants (`prefp`, created through the public API), the platform session, and the suspended tenant (`prefq`), reading the rows back from the disposable database.
- `helpers/pagination.js`: the `PAG-*` checks of cursor pagination (Repositories, both Pipelines lists, tenant audit log, and the Root Console lists `/platform/tenants` and `/platform/audit-logs`; the cursor is HMAC-signed, the runner passes the API `CURSOR_SIGNING_SECRET` with two keys and the suite the keys it forges cursors with, `SECURITY_CURSOR_KEYS`; `PAG-017` also runs the rotation procedure and the secret configuration boundary in process): two fresh tenants (`pagp`, `pagq`) built through the public API and the seeded demo tenant's two workspaces, rows written to the disposable database with deliberately tied sort keys (names, times) and NULL last-event times; cursor walks compared with the offset result for every sort, rows inserted between two requests (with an offset-paging control that shows the shift), tampered/foreign/cross-tenant cursors, hidden-workspace and 401/403/404 behavior.
- `helpers/execution-db.js`: the execution state machine in the database and its helpers (`EXECDB-011..018`, SPEC executions §7.3, §14.1 part B, in process, two tenants with two workspaces each from the `pipeline-db.js` factories): every ordered pair of statuses against the 11 transitions of SPEC 6.1 (a well-formed UPDATE per pair), terminal immutability, snapshot and one-time columns, `status_rev`, `quota_released_at`, `cancelling` unwritable, SQL/`@qmentisai/shared` parity (`EXECDB-012`), composite tenant-safe chain foreign keys (`EXECDB-013`), children of finished executions and insert-only history (`EXECDB-014`), lease epochs, the attempt fence and the orchestrator marker (`EXECDB-015`); `EXECDB-016..018` call the real claim, renew, reclaim, fence and transition-with-quota-release helpers of `@qmentisai/db` concurrently (exactly-once claim, stale refusal, zombie holder rejected, quota released once). `driveExecution` walks an execution legally to `running` or an outcome for the checks that need such rows (the machine no longer allows `queued -> running`). The marker check deletes only its own `suite.marker.*` rows (trigger disabled in a transaction) so the permanent first-enable marker of the orchestrator is never present at suite start.
- `helpers/orchestrator.js` and `helpers/orchestrator-checks.js`: the execution orchestrator (`EXE-*`, SPEC executions §14.1 and §17.z, part C) IN PROCESS against the disposable database and the local GitHub stub: the real orchestrator, scan task handler, ownership verifier and outbox, a `pump` that plays the broker (hands the outbox rows of the `scan`, `scan-untrusted` and `pipeline` queues to the handlers), the stub's installation tokens and archive-by-SHA endpoint (302 to a pre-signed URL that must receive no `Authorization`), and a deterministic TEST ENGINE registered only here (no engine ships with the platform; it reads `qm-test.json` at the archive root to fail, retry or hang). The checks cover ownership re-validation of every message type, claim re-validation, exactly-once claim, the snapshot, credential absence (fork and trusted), archive hardening, outcome aggregation and retries, `resolutionEligible`, timeouts, the message allow-list, lease reclaim exactly once, zombie fencing, heartbeat and the TTL rule, `worker_lost` decisions, quota on lease loss, the one-time first-enable sweep (`EXE-032` must run on a database without the marker: it asserts that) and the never-start-a-stale-run rule; the spec ids `EXE-021/022/023` and the API checks belong to later parts, `EXE-034..036` (aggregation, timeouts, flag off) are added by part C beyond the spec list.
- `helpers/cancel-retry-checks.js`: cancellation and retry (`EXE-037..045`, SPEC executions §14.1 EXE-008..010 and §17.aa, part D) IN PROCESS over the orchestrator world: the service layer of `apps/api/src/modules/executions` (cancel and retry; the HTTP routes are part G) with the real audit service, outbox and entitlements, the real orchestrator and scan handler, and the test engine (which gained `delay`, `delayThenTransient` and `deaf` scripts). The checks cover quota released exactly once under N parallel cancels and cancels racing the claim and the lease reclaim, immediate and graceful cancellation (what is aborted when, partial results kept, no task or retry attempt after the request, the deadline winning over a waiting cancel, a hung attempt force-closed and its late write rejected), the cancel request while preparing (including the narrowest window before the task transaction and a stale holder), retry pinning the commit and the snapshot, fork retries staying `untrusted_fork`, retry idempotency, quota and gates, the chain cap, the concurrency policy and the 404 of another tenant's execution. `DAL-249..262` (in `direct-repos.js`) cover the new shared cancel functions, `cancelUnstarted` and the write-side repository of the executions module.
- `helpers/exec-http-checks.js`: the executions HTTP API (`EXE-055..068`, SPEC executions §8.1 and §17.ae, part G) over HTTP on the Pipelines world (`pipWorld`, the edge tenant, per-role sessions, custom-role members), rows written to the disposable database: cross-tenant and hidden-workspace 404 identical to a missing id, 403 for missing permissions with audited denials, list scope and filters that cannot widen it, cursor binding and tampering, list walk against database order (ties, microsecond-apart rows, inserts), identifiers never from the client, session separation, retry idempotency and gates, cancel semantics and quota once, suspended tenant, absence of credentials and internal keys (key allow-lists), logs, events and detail.
- `helpers/logs-db-checks.js` and `helpers/exec-store-checks.js`: execution logs, artifacts and retention (part E): database integrity of the capped tables, the LogStore and ArtifactStore (caps, redaction, write fence, scoped reads), logs written by the workers, the retention purge and its gates, artifact reference validation.
- `helpers/exec-audit-checks.js`: part I of the Executions plan (`EXECDB-026`, `EXE-071..076`, SPEC executions §14.1 and §17.ag) IN PROCESS over the orchestrator world: the enumerations that stop a new table (composite tenant keys), route (the real router against the HTTP checks' `ROUTE_MANIFEST`), message type (strict schema and ownership forgery per type) or repository function (the DAL list or a written exemption) from shipping without checks, the end-to-end proof that an `untrusted_fork` execution leaves no credential in any surface (stored rows, realtime hints, API responses, worker log, scan contexts), the quota unit released exactly once on every cancel path, and the atomicity of audit entry, event, message and change under forced failure.
- `helpers/sbom-checks.js`: the SBOM engine and the `unsupported` task status (`EXE-046..050`, SPEC executions §17.ab) IN PROCESS over the orchestrator world, with the PRODUCTION registry shape (`w.sbomRegistry()`: only the real built-in SBOM engine, wrapped to record what it is given): the engine receives only `{ sourceDir }` and no credential or environment value (trusted and fork runs, plus a source guard against environment, process, network and `eval`), unsupported tasks never fail the run (SBOM only succeeds, SBOM + SCA is partial, nothing runnable fails before any fetch with the unit given back once, an outcome table), a fork SBOM run goes to `scan-untrusted` with the same credential sweep as `EXE-019`, hostile archives (lifecycle scripts next to a marker-writing script, malformed, deeply nested and oversized lockfiles, an external entity, `__proto__` keys, symbolic links) are only data, and the output is sorted, de-duplicated and tenant-scoped. `EXECDB-019` (in `execution-db.js`) and `DAL-263` (in `direct-repos.js`) cover the database rules of `unsupported` and `tasks.markUnsupported`.
- `helpers/pipeline-db.js`: database integrity of the Pipelines + Triggers tables (`PIPDB-*`, in process): two tenants with two workspaces and repositories each, row factories, and 14 table-driven checks (composite foreign keys, unique identities, immutability triggers, CHECK constraints, RESTRICT), each with a control.
- The Pipeline API checks (`PIP-*`, SPEC pipelines-triggers §14.1, part C) live in `security.test.js` (section 13) and run over HTTP: the world (`pipWorld`, `capWorld`) is built through the public API (GitHub stub, linking and connecting, per-role sessions of the seeded demo tenant, a second tenant) and read back from the disposable database. `capWorld` is a fresh tenant with `pipelines.max` = 2 and `scans.monthly` = 1 for the limit checks and, last, the suspension check.
- The router checks (`PIP-005..008`, `PIP-015..017`, `PIP-028`, `PIP-035..039`, SPEC pipelines-triggers §6.2, part D) live in `security.test.js` (section 14). They deliver SIGNED webhooks through the running API and hand the stored `scm.*.received` envelope to the router IN PROCESS (`createPipelineTriggerHandler` behind the ownership verifier, as the `pipeline-triggers` consumer does), against the disposable database; the world (`rtWorld`) is built through the public API: tenant R with two workspaces, tenant X connecting the same GitHub repository id, tenant Q with one scan per month. No broker is used.
- The closed pull request checks (`PIP-056..059`, SPEC pipelines-triggers §5.4, §5.9b, fix-list 4) use the same router world (`rtWorld`: repositories `prc`/`prd` in workspace one, `prw` in workspace two, the same GitHub repository id `prc` connected by tenant X, six pipelines with and without a pull request trigger). They deliver signed `opened`/`synchronize`/`closed` webhooks, mark some runs running or finished in the database and hand the stored `closed` envelope to the router in process, including replays and two concurrent replays.
- The schedule checks (`PIP-012`, `PIP-013`, `PIP-040..050`, SPEC pipelines-triggers §5.6, §6.4, part E and its 2026-11-13 fixes: `PIP-048` schedule decision rows, `PIP-049` per-slot jitter, `PIP-050` fall-back days through the handler) live in `security.test.js` (section 15). The world (`schWorld`) has tenant S (two workspaces), tenant X (the same GitHub repository id and cron) and tenant Q (one scan per month). `helpers/schedule-fixtures.js` holds the deterministic DST fixtures (Europe/Berlin and America/New_York, both 2026 transitions, fixed instants) as table data for `PIP-043`, `PIP-044` and `PIP-050` (also the whole-day fire counts of the fall-back days and the jitter fixtures); there is no separate feature-test suite.
- The part G consolidation checks (`PIP-051..055`, SPEC pipelines-triggers §16 "part G, suite coverage matrix") live in `security.test.js` (section 16) over the same world as the Pipeline API checks. `PIP-051` installs, then removes, two database triggers in the disposable database (one rejecting the audit insert, one failing the change at COMMIT) to prove atomicity. The SPEC holds the matrix from every item of §14.1 to the checks that cover it and the table function -> catching checks of the mutation sweep.
- `helpers/direct-repos.js`: data-access isolation (`DAL-*`): builds four tenants directly in the database (X owns the data, including one pipeline with a version, a trigger, a queued and a running execution and a trigger decision, Y is the "wrong" tenant, Z holds the uninstall fan-out and notification fixtures, V two workspaces with revoked repositories for the shared restore functions of `@qmentisai/db`) and calls every tenant-scoped repository function in process with another tenant's id (table-driven, one check per function; `DAL-154..187` are the pipelines module and the pipeline scope resolver and ownership check, `DAL-188..198` the trigger router's worker-side repository (`apps/workers/src/pipeline/repository.js`), `DAL-199..207` the schedule handler's (`apps/workers/src/scheduler/schedule-repository.js`; its two platform scans have no tenant argument by design), `DAL-208..210` the advisory-lock keys, `DAL-211..216` the parent-chain functions with the right tenant but the wrong repository or workspace, `DAL-217..218` the ownership check per workspace and repository (part G), `DAL-221` the closed pull request cancel function, `DAL-222..223` the user preference repository; includes the workspace-link, allow-list and tenant-setting functions, the uninstall/suspension fan-out of the scm worker and the notification recipient lookup).
