# ADR-007: Replace Fastify with Express 5

- **Status:** Accepted (2026-11-11, on the product owner's instruction). **Implemented on branch `feat/express-migration` (2026-11-11): `apps/api` runs on Express 5; all acceptance gates below passed; pending merge.** The Fastify-era contract stays in `docs/api/*fastify-baseline*` as the frozen reference.
- **Date:** 2026-11-11
- **Decision owners:** Product owner (decision); Claude Code (documentation, baselines and the implementation)
- **Supersedes:** the framework choice in `docs/technical/TECH_STACK.md` ("Backend framework note") and the Fastify wording in `BACKEND_ARCHITECTURE.md`, `ADR-002` (its modular-monolith decision stands; only the word "Fastify" is superseded) and `CLAUDE.md`.

## Context

Phases 1-4 built `apps/api` as a modular monolith on **Fastify 5**: 9 modules, 61 operations, plugin-based composition, hook-based authentication, tenant context and authorization, Zod validation through Fastify's schema compilers, and OpenAPI generated by `@fastify/swagger`. `TECH_STACK.md` fixed Fastify as the backend framework and told tools not to "silently replace it"; this ADR is the explicit, recorded replacement.

**What depends on Fastify today** (and therefore changes):

| Area | Where | Fastify mechanism |
|---|---|---|
| Composition and encapsulation | `apps/api/src/app.js`, `plugins/*`, `modules/index.js`, `plugins/modules.js` | `fastify-plugin`, `register`, per-module prefix, decorators (`app.infra`, `app.auth`, `app.authz`, `app.audit`, `app.entitlements`) |
| Request pipeline | `plugins/authentication.js`, `plugins/authorization.js`, `plugins/correlation.js` | `onRequest` / `preHandler` hooks, `request.principal`, `request.authz`, `request.routeOptions.config` |
| Startup guard "every route declares its audience" | `plugins/authentication.js` | `onRoute` hook (the server refuses to start otherwise) |
| Validation | `lib/validation.js` | Zod validator and serializer compilers; validation runs before the `preHandler` hooks |
| Responses and errors | `plugins/envelope.js`, `plugins/error-handler.js` | `reply.success` / `reply.paginated` decorators, `setErrorHandler`, `setNotFoundHandler` |
| OpenAPI | `plugins/openapi.js`, `lib/openapi.js` | `@fastify/swagger` with a Zod-to-JSON-Schema transform |
| Cookies, CORS, logging, body limits | `@fastify/cookie`, `@fastify/cors`, Fastify's built-in Pino logger, `bodyLimit` | plugins and server options |
| Tests and tooling | `scripts/snapshot-contract.js` | `app.inject`, `app.swagger()` |

**What does not depend on Fastify:** services, repositories, policies, mappers, constants, Zod schemas, the authorization engine (`@qmentisai/shared`), `@qmentisai/db`, `@qmentisai/infra`, `@qmentisai/contracts`, the workers and both frontends.

## Decision

Replace Fastify with **Express 5** as the HTTP transport of `apps/api`. Keep the modular monolith (ADR-002), the module folder convention, Zod at every boundary, Prisma behind repositories, Pino for logging, and OpenAPI as the public contract. The HTTP **contract does not change**: same 61 operations, paths, statuses, envelopes, cookies and error codes, as recorded in `docs/api/`.

**Rationale as stated by the decision owner:** none was given with the instruction that requested this ADR. The owner should record the reasons here. Candidate drivers, *unconfirmed*: team familiarity and ecosystem breadth, a simpler explicit-middleware model, and easier raw-body handling for provider webhooks (Phase 5).

## Migration approach: transport layer only

**Unchanged** (the migration must not touch their behavior): services, repositories, policies, mappers, constants, event declarations, Zod schemas, `@qmentisai/shared` (permission catalog, roles, resolver, `can`, navigation), `@qmentisai/db`, `@qmentisai/infra`, `@qmentisai/contracts`, workers, frontends.

**Rewritten:** `app.js`, `server.js`, `plugins/*`, each module's `routes/` and `controllers/` (signatures change from `(request, reply)` to `(req, res)`), `lib/validation.js`, `lib/openapi.js`, the request plumbing in `auth/cookies.js` and `auth/context.js`, the error handler, and the contract-snapshot tooling.

**Fastify feature to Express replacement**

| Fastify | Express 5 replacement |
|---|---|
| Plugins and encapsulation | An app factory `createApp({ config, modules })`; each module exports a factory returning an Express `Router`, mounted at its prefix; dependencies are passed explicitly (no hidden global state, as `BACKEND_ARCHITECTURE.md` already requires) |
| `onRoute` audience guard | A single route-registration helper (`defineRoute({ audience, permission, schema, handler })`) that **requires** `audience` and throws at startup otherwise, with the same placement rules (platform audience only under `/api/v1/platform/`) |
| `onRequest` / `preHandler` hooks | One **fixed-order middleware chain** (see below), assembled only by `defineRoute` so no route can skip a step |
| Zod compilers (params, query, body) | A `validate({ params, query, body })` middleware that stores the parsed values (Express 5's `req.query` is read-only) |
| `reply.success`, `reply.paginated` | `res.success`, `res.paginated` helpers with the same envelopes |
| `setErrorHandler` / `setNotFoundHandler` | An error-handling middleware and a catch-all JSON 404; same stable codes and the same safe messages (`AppError`, `ERROR_HTTP_STATUS` are reused) |
| `@fastify/swagger` | An OpenAPI document generated from the route registry's Zod schemas (reusing `toOpenApiSchema`). **Open decision:** hand-written generator or a library |
| `@fastify/cookie`, `@fastify/cors` | `cookie-parser` and `cors` (or equivalent small code); cookie names, paths and flags unchanged |
| Fastify's Pino integration | `pino-http` or a small request logger; the same redaction paths and `correlationId` |
| `bodyLimit` | `express.json({ limit })` plus handlers that keep the existing 400/413/415 error codes |
| `trustProxy` (not configured today) | `app.set("trust proxy", ...)` driven by configuration (closes an audit gap) |

**Required middleware order as originally proposed** (superseded by the order recorded under *Implementation outcome*, where validation follows authentication on the owner's instruction):

1. correlation id, 2. request logging, 3. body parsing with limit, 4. CORS, 5. cookies, 6. CSRF/Origin check on unsafe methods, 7. input validation, 8. authentication by route audience (`public`, `user`, `tenant`, `platform`), 9. tenant context from the session, 10. `authorize(permission, scope)` (404 for not visible, 403 for not permitted), 11. handler, 12. envelope/error handler.

**Acceptance gates** (nothing is cut over until all pass):

1. `pnpm test:security` passes **unchanged** (ADR-008: 68 checks, 16 controls, 1 integrity test), run against the Express server.
2. The OpenAPI document generated by the Express app is diffed against `docs/api/openapi-fastify-baseline.json`; every difference is either removed or explained and approved. The per-operation table in `docs/api/contract-fastify-baseline.md` is regenerated and compared (method, path, permission, success status, error codes, envelope shape).
3. `pnpm lint`, `pnpm build` and `pnpm format:check` pass.
4. The tenant and Root Console browser flows pass unchanged (the frontends are not edited).
5. A smoke comparison of p95 latency on the list endpoints before and after (informational; no hard threshold, because the throughput difference is a known trade-off).

**Sequence:** work on a branch; keep the Fastify entry point until cutover and add the Express entry point beside it so the suite can target either (the runner will take the entry point from configuration); port in this order: skeleton and error handling, correlation/logging/CORS/cookies/CSRF, authentication and tenant context, authorization, then modules one at a time, then the OpenAPI generator; remove Fastify dependencies last; merge as one merge (or squash) commit.

**Rollback:** `git revert` of the migration merge commit. There is no data or schema migration, no change to session cookies or token format and no change to the API contract, so a revert is safe at any time and invisible to users and frontends.

## Alternatives considered

1. **Keep Fastify** (status quo): the best-fitting framework for the current design (schema-first, encapsulated plugins, fast), already built, verified and recorded. This option remains the lower-risk one; it was not chosen by the owner.
2. **Express 5** (chosen).
3. **Other frameworks** (for example Hono or Koa): not evaluated. NestJS remains excluded by `docs/README.md` (no TypeScript, no decorators-based framework).

## Consequences

### Positive
- The most widely known Node HTTP framework and middleware ecosystem.
- Explicit middleware makes the request pipeline a single readable chain; async errors are forwarded automatically in Express 5.
- Simple per-route raw-body handling for webhook signature verification (Phase 5).
- A forced, reviewed re-implementation of the request pipeline, with the security suite and API baselines as safety nets.

### Negative / trade-offs
- **Rework cost and risk** for every route, controller, plugin and the OpenAPI generation; the highest-risk part is the middleware order (authentication and authorization are enforced there).
- Loses Fastify's built-in schema compilation, encapsulated plugin model, first-party OpenAPI plugin and logger integration; each must be replaced or hand-written (see the table).
- Lower raw throughput than Fastify. Today's response schemas are documentation only (serialization was already `JSON.stringify`), so no response validation is lost.
- New dependencies to justify (likely `express`, `cookie-parser`, `cors`, `pino-http`, optionally `helmet`); each needs an entry in `TECH_STACK.md` with its reason and a pinned version. `@fastify/*` and `fastify*` dependencies are removed at cutover.
- Two transports coexist for a while (extra surface and tooling), until cutover.
- `engines`/`.nvmrc` must stay compatible with the chosen versions.

## Security and operational impact

- Authentication, tenant context and authorization move from hooks to middleware: the migration is blocked on the security suite and on a code-level guarantee that only `defineRoute` can register routes.
- Express does not enforce the "audience declared" startup guard by itself; `defineRoute` must (acceptance gate 1 includes a startup-refusal check to be added to the migration's own verification).
- Opportunity to close audit gaps while the pipeline is rewritten: `trust proxy`, security headers (`helmet`) and a global rate limit are *decisions for the migration spec*, not part of this ADR.
- No change to sessions, cookies, database, queues, workers or frontend behavior.

## Decisions taken with the migration (by the owner's dependency list, 2026-11-11)

| Topic | Decision |
|---|---|
| OpenAPI generation | `@asteasolutions/zod-to-openapi` 7.3.4 over the route kit's table (v7 is the last line supporting Zod 3). Served at the same path `/api/v1/openapi.json`; `swagger-ui-express` adds `/api/v1/docs` when `OPENAPI_ENABLED` |
| Middleware libraries | `cors`, `cookie-parser`, `pino-http`, `helmet`, `express-rate-limit` + `rate-limit-redis` adopted (pinned, justified in `TECH_STACK.md`) |
| `trust proxy`, `helmet`, global rate limit | Adopted now: `TRUST_PROXY` (hop count or addresses; `true` refused), `RATE_LIMIT_WINDOW_MS`/`RATE_LIMIT_MAX` (default 600 per minute per IP, before authentication, Redis-backed when configured, probes exempt) |
| Side-by-side entry points | Not needed: the migration is one branch; `src/server.js` stayed the entry point so the security suite ran unchanged |
| Validation vs authentication order | **Changed on the owner's instruction** (see differences below) |

## Implementation outcome (verified 2026-11-11)

**Structure.** `createApp({ config, modules })` in `src/app.js` (returns `{ app, ctx, routes, openapi, close }`); `src/server.js` listens and shuts down gracefully (stop accepting, drain, then close RabbitMQ, Redis, Prisma; exit 0). `src/lib/route-kit.js` is the only way to register a route: it requires `config.audience`, enforces the platform-path placement rules at startup, rejects duplicates, mounts tenant routes on a router at `/api/v1` and platform routes on a separate router at `/api/v1/platform`, and assembles each route's chain. `src/middleware/` holds correlation, request logging, security (helmet, global rate limit, body parsing), authentication (per-audience chains, CSRF origin check, CORS, cookies), authorization, envelope and error handling; `src/runtime/` holds the factories that replaced plugins (readiness, infrastructure, audit, entitlements, module registration). Modules keep their folders; `routes/` still declares the same options (`config.audience`, `preHandler`, Zod `schema`) and controllers, services and repositories are unchanged.

**Middleware order** (global, then per route): correlation id, pino-http (redaction), [Swagger UI when enabled], helmet, CORS, global rate limit, cookies, envelope helpers, body limit (413) and content-type guard (415), CSRF origin check; then per route: authentication by audience, tenant context (tenant routes, from the session only), `validate(zod)`, `authorize(permission, scope)` (404 hidden / 403 forbidden), handler; then JSON 404 and the centralized error handler.

**Gates (all passed).**
1. Contract parity: `pnpm contract:parity` compares `contract-express.json`/`openapi-express.json` with the Fastify baselines: 61 operations, 0 differences in path, method, audience, permission, success status, documented error statuses, error codes, request parts, envelope; OpenAPI schemas equal after normalizing generator spelling (`docs/api/parity-report.md`).
2. `pnpm test:security`: 85 tests (68 checks, 16 controls, integrity) pass, unchanged, against the Express server.
3. `pnpm lint`, `pnpm build`, `pnpm format:check` pass; no Fastify import remains anywhere.
4. Browser flows against the Express API on a throwaway PostgreSQL: login for each seeded role and navigation (56 checks), T-06/07/08/40/44 and tenant flows (49), R-04/05/06 (41), Root Console login/MFA/navigation (30); 0 server errors. Gate 5 (latency comparison) was not run (informational).

## Behavior differences from the Fastify transport (reviewed; none changes the documented contract)

1. **Validation now runs after authentication and tenant context** (owner's order). An unauthenticated caller sending invalid input gets `401 UNAUTHENTICATED` instead of `400`; a tenant route with a suspended tenant answers `403 TENANT_SUSPENDED` before validating. Public routes (login, MFA) still validate first. `API_STANDARDS.md` is updated.
2. Request with `Content-Type: application/json` and an empty body: Fastify answered 400 before the route; now routes that declare a body schema answer `400 VALIDATION_FAILED`, routes without one (for example logout) succeed.
3. Added: helmet security headers, a global per-IP rate limit (`429 RATE_LIMITED`), `TRUST_PROXY`, Swagger UI at `/api/v1/docs` (only with `OPENAPI_ENABLED`, relaxed CSP on that path only), ETag disabled. Login throttling is unchanged.
4. Body errors keep their codes: oversize `413 PAYLOAD_TOO_LARGE`, malformed JSON `400 BAD_REQUEST`, other content types with a body `415 UNSUPPORTED_MEDIA_TYPE` (emulated by a guard).
5. OpenAPI: generated by a different library. Success response descriptions are `OK`/`Created` instead of `Default Response`; strict objects no longer carry `additionalProperties: false`; free-form maps are spelled `{ nullable: true }`. The error responses documented per audience are unchanged.
6. Log lines come from pino-http: same redaction, `correlationId`, method, path and status; message strings may differ slightly from Fastify's.
7. Routing is case-sensitive and strict (no trailing-slash matching), as before; unknown paths and methods answer the JSON 404 envelope.
