## Context

`docs/STATUS_PHASE_1-4.md` found that the security-critical behavior (tenant isolation, the 404/403 rule, platform/tenant session separation) had been verified only by scratch scripts that lived outside the repository. Nobody else could re-run them, and a change to the request pipeline could silently regress them. ADR-007 (Fastify to Express 5) rewrites exactly that pipeline, so the checks must exist in the repository, must run against any HTTP transport, and must be proven to fail when the behavior breaks.

## Decision

Add a committed **security regression suite**, run with `pnpm test:security`.

**Allowed scope: ONLY the areas below (the fifth to the twelfth were added by the owner on 2026-11-11 and 2026-11-12), run by ONE command, `pnpm test:security`.** Feature tests, unit tests, UI/browser tests and test-case directory structures for anything else stay out of scope (see *Out of scope* and *Rules for contributors*).

**In scope (and only this):**

1. Tenant isolation: another tenant's resources by id (read, change, delete, assign, add as member), list leakage, tenant never taken from a header, query or body.
2. Authorization outcomes: a workspace the caller cannot see answers **404** with a body identical to a non-existent one; a visible resource without the permission answers **403**; escalation guard (SOD-3).
3. Platform/tenant session separation: tenant session on platform routes (404), platform session on tenant routes (401), no session (401), platform session before MFA (401 `mfa_required`, no data), cookie-name confusion, cross-audience sign-in, cross-site Origin (CSRF) refusal.
4. Segregation of duties: no self-escalation (SOD-3, check `AUTHZ-015`, part of the 68). SOD-1 (a reviewer cannot approve their own decision) and SOD-2 (a decision awaiting approval cannot be edited by its reviewer) get checks **in the same work item that builds the review/approval workflow**, because they cannot be exercised before it exists; adding them changes the count of checks and requires updating this ADR and the integrity test.

5. Sign-in and MFA throttling (added 2026-11-11 with ADR-010, owner instruction): progressive delay after the free attempts, identical behavior for existing and non-existing accounts (no enumeration), per-IP limit, refused attempts do not extend the wait, no hard lock. Checks `THR-001..009`.
6. Tenant restore window (added 2026-11-11, AUTHORIZATION Q25): who can restore a deactivated tenant and when, the tenant stays unusable while deactivated and after the window ends, `TENANT_DEACTIVATION_EXPIRED`. Checks `RST-001..006`. This is lifecycle/session separation behavior, kept to six checks.

7. Secret storage foundation (ADR-009): tenant isolation of secret references, AAD binding, no plaintext at rest, in views or in audit entries, message guard. Checks `SEC-001..009`. They run **in-process** against the disposable database (the runner passes `SECURITY_DATABASE_URL`) and import the secret store wiring, because the store has no HTTP surface yet; this is the one place the suite is not purely black box, and it ends when an HTTP surface exists.

Twenty-one checks; the runner sets high global and write limits and a 200-request, 5-second auth window so the suite itself is never throttled.

Isolation: another tenant's pipeline by id on every verb (get, edit, publish, enable, disable, delete, run, versions, executions, decisions) is the same 404 as a missing id, a hidden workspace the same, a visible workspace without the key 403 (`PIP-001..004`, creation under a foreign or hidden repository and a smuggled `tenantId`/`workspaceId`, list and filters inside the caller's workspaces). Configuration (R-8): run_with_credentials, `dast`, `assetDiscovery`, unknown keys and command-, script-, install-, build- or hook-like keys at every level are 400, and the published OpenAPI schema of the configuration has no such property and `additionalProperties: false` on every object (`PIP-009`, `PIP-027`). Fork policy: `pipeline.manage_fork_policy` is required to set a policy other than `skip` (Manager and Dev Lead 403 with `fork_policy_requires_permission` and nothing written, Admin and Lead succeed, setting `skip` or leaving an existing value needs only `pipeline.manage`) and every change is audited with old and new value (`PIP-026`). Versions: immutable through the API (no route), an edit is a new version, an earlier execution's snapshot is unchanged, concurrent publishes with one `expectedVersion` give exactly one winner (`PIP-018`, `PIP-019`). Manual run: `execution.run` (Viewer, Developer, Analyst 403; hidden 404; Lead, Dev Lead, Manager, Admin 202 with one queued execution and one message), idempotent by `Idempotency-Key` (required), refused with 409 for a disabled pipeline, a disabled, unavailable or disconnected repository and an archived workspace with nothing created and nothing consumed, `scans.monthly` and entitlement blocks 403 with nothing created, a suspended tenant `TENANT_SUSPENDED`, and every denial audited as `execution.manual_denied` in the caller's tenant only (`PIP-010`, `PIP-011`, `PIP-014`, `PIP-029`, `PIP-030`, `PIP-034`). Limits and history: `pipelines.max` (including concurrent creates), soft delete (history stays, queued requests cancelled and their quota returned, a running execution refuses it), audit entries with version numbers and path-only diffs, the message payload and its ownership check, the dry-run without side effects, platform sessions refused (401) and no platform route, the repository DTO's real `pipelineCount` (`PIP-020..025`, `PIP-033`). `DAL-154..187` call every new tenant-scoped repository function in process with another tenant's id and with the right tenant and the wrong workspace or repository, each with a control. Router, scheduler and producer checks belong to parts D and E.
14. Pipeline trigger router (added 2026-11-13, SPEC pipelines-triggers §6.2, §14.1 and §13.3 part D): signed webhook deliveries go through the real API (webhook, `scm_events`, outbox) and the stored `scm.push.received` / `scm.pull_request.received` envelope is handed IN PROCESS to the router exactly as the `pipeline-triggers` consumer does (parse, ownership verifier, handler), against the disposable database, like the SCM-043 pattern. Three tenants are built through the public API: R (two workspaces, one repository per scenario), X (connects the same GitHub repository id through its own installation) and Q (one scan per month). Isolation: the same external repository id in two tenants only creates executions for the owning tenant, in both directions, and never for other repositories or workspaces (`PIP-005`, `PIP-006`); forged messages (another tenant's id with the repository or workspace of a different one) are refused with `resource-not-in-tenant` by the consumer's ownership check and by the router alone (`PIP-007`). Fan-out and exactly-once: one event with three matching pipelines creates three executions and three messages, one per pipeline on a duplicate delivery, a redelivered message and a crash between two pipelines (`PIP-016`). Fork rule: the default policy skips a fork and an unknown fork status with a decision row, a same-repository pull request runs, `run_without_credentials` creates an `untrusted_fork` execution whose message carries only ids, enums and short strings, drafts are skipped by policy (`PIP-008`, `PIP-035`); branch include/exclude, tag rules and created/forced/deleted refs (`PIP-036`); decision rows are exactly one per pipeline and delivery and non-matches leave nothing (`PIP-038`). State: disconnected, unavailable and disabled repositories, disabled and deleted pipelines and disabled triggers create nothing (the consumer re-checks the state after it changed between publication and consumption), suspended and deactivated tenants are dead-lettered `tenant-not-usable`, an archived workspace leaves a decision row (`PIP-015`, `PIP-017`), and the SCM producer publishes no push or pull-request event for a repository that is not `active` and enabled while repository events still reach an `unavailable` one (`PIP-028`). Quota and concurrency: a quota or entitlement refusal of an unattended trigger is a `blocked` row with one audit entry per pipeline, reason and day, no message and no unit (`PIP-037`); supersede, queue and skip, late events (`stale_event`) and the quota arithmetic (`PIP-039`). Data-access isolation of the router's functions: `DAL-188..198`. Mutations swept in a scratch copy (2026-11-13): dropping the tenant filter of the pipeline list and of the repository state read, treating an unknown fork status as non-fork, skipping the repository status re-check, dropping the quota consume, dropping the idempotency handling and reverting the producer condition are each caught.

Pipeline schedules (added 2026-11-13, SPEC pipelines-triggers §5.6, §6.4, §14.1 and §13.3 part E): the scheduler's due-schedule handler runs IN PROCESS against the disposable database with a FIXED clock (instants in 2026, all before the real date, so the planned times the API computes from the real clock are never due), after pipelines and schedules were created through the public API and the due state was set in the database; tenants S (two workspaces), X (the same GitHub repository id and the same cron) and Q (one scan per month). Re-validation at fire time: a repository that became disconnected, unavailable or disabled, an archived workspace, a suspended tenant, a disabled or deleted pipeline, and a trigger removed or disabled by a later configuration version create no execution and no message, advance or park the schedule, and the restored state fires once (`PIP-012`). Exactly once: two handlers racing on one due trigger, the same slot handled again and a crash before the commit (simulated by failing the advance inside the transaction) leave one execution and one message per slot and no quota unit behind (`PIP-013`). Quota exhaustion at fire time: `blocked` rows, one audit entry per pipeline, reason and day, no message, no unit, another tenant unaffected (`PIP-040`). Isolation: identical crons on the same GitHub repository id in two tenants and a second workspace each fire only their own pipeline, with their own tenant, workspace and repository on the row and the message, and the per-tenant share of a tick is honored (`PIP-041`). API validation: too-frequent crons (also once a daylight-saving change is counted), unknown time zones, seconds, `@reboot`, `L`, `W`, `#` and never-firing schedules are 400 and write nothing; `next_fire_at` is stored in UTC when a schedule is created, edited or enabled and cleared when disabled or removed (`PIP-042`). Schedule policy skips write one `schedule_slot` decision row per trigger and slot and stay idempotent, tenant-bound and execution-free (`PIP-048`); the jitter is `hash(triggerId + slot) mod window`, deterministic and inside the window, and the slot key never moves (`PIP-049`); fall-back days through the handler give one execution per real UTC hour for a wildcard hour, while step hours N > 1 and named hours fire once in the repeated hour (`PIP-043`, `PIP-050`, follow-up 2026-11-13). DST: deterministic fixtures for Europe/Berlin and America/New_York across both 2026 transitions (gap fires once at the gap end, overlap once at the first occurrence, the real minimum gap, the missed-run plan) as table-driven assertions and through the handler (`PIP-043`, `PIP-044`; fixtures in `helpers/schedule-fixtures.js`, no feature-test suite). Missed runs, request shape and ref resolution, and the tick job (`PIP-045..047`). Mutations swept in a scratch copy (2026-11-13), each caught: the tenant condition removed from the due-claim query (`DAL-199`), the pipeline read (`DAL-202`) and the slot lookup (`DAL-204`); the repository status re-check skipped (`PIP-012`); the trigger-disabled and trigger-removed re-checks dropped (`PIP-012`); the unique-slot handling dropped (`PIP-013`); the quota consume dropped (`PIP-040`); the gap treated as skipped (`PIP-043`, `PIP-044`). The database unique slot is a backstop: with the pipeline lock and `SKIP LOCKED` removed the outcome checks still see one execution per slot.

Pipelines: consolidation (added 2026-11-13, SPEC pipelines-triggers §16 "part G, suite coverage matrix"): HTTP checks over the same world as area 13 for what the audit of §14.1 found missing. `PIP-051` forces a failure of the audit insert (a database trigger on the disposable database) and, separately, of the change itself at COMMIT (a deferred constraint trigger), and requires that create, publish, disable, delete and a manual run leave no row, version, message, quota unit or audit entry; `PIP-052` reuses one `Idempotency-Key` across tenants and pipelines; `PIP-053` soft-deleted pipelines of a hidden workspace or another tenant; `PIP-054` role, permission, member and assignment fields are rejected and nothing of the tenant's authorization changes; `PIP-055` a router message whose fork flag is missing or not a boolean is refused or treated as a fork. In the data-access area, `DAL-208..210` probe the advisory-lock keys from a second connection (held for the holder's tenant, free for another), `DAL-211..216` call the parent-chain functions with the right tenant and workspace but the wrong repository (or workspace), `DAL-217..218` do the same for the ownership check of `pipeline.execution.requested`.

Also covered, as part of areas 1 to 3: tenant suspension takes effect immediately and does not affect another tenant (`SUSP-001..003`, part of the 68).

## Design

- **Black box over HTTP.** The suite talks to a running API with `fetch`; it imports no API code. The same checks therefore run unchanged against Fastify now and Express after ADR-007.
- **Runner** (`apps/api/scripts/security-suite.js`): provisions a **disposable PostgreSQL** (an ephemeral local cluster built with `initdb`/`pg_ctl` from `PG_BIN_DIR`, `/usr/lib/postgresql/*` or `PATH`, in a temporary directory on a free port; no Docker), applies migrations and the seed, starts the API as a child process with a clean environment, runs the tests, and always tears everything down. Alternatively `SECURITY_TEST_DATABASE_URL` selects an existing database, **refused unless its name contains "test"**; its URL is never printed. The runner starts the API with a short throttle curve (3 free failures, waits of 1 s, 2 s, 4 s cap) so the THR checks finish in seconds; production defaults are in ADR-010; the restore window is set to 4 s (`TENANT_DEACTIVATION_RETENTION_SECONDS`) for the `RST` checks. Exit codes of the runner: 0 passed, 1 a check failed, 2 the environment is unusable (with an explanation); pnpm reports 1 for any non-zero exit, so the message distinguishes them.
- **Secrets are random per run** (mock passwords, MFA code); none is stored in the repository.
- **World built through the public API only:** tenant A is the seeded demo tenant; tenant B is created through `POST /platform/tenants`, its administrator is invited and accepts, then creates a workspace, group, custom role and workspace role assignment. Everything created carries a random suffix, so the suite can be re-run on the same disposable database.
- **Framework:** `node:test` (built into Node 22). **No new dependency.**
- **677 checks** (672 plus 5 of numbered pages, 2026-11-16: `EXE-069`, `EXE-070`, `DAL-289..291`; 672 = 643 plus 29 of the executions HTTP API, part G, 2026-11-16: `EXE-055..068`, `DAL-274..288`; 643 = 625 plus 18 of the realtime server, part F, 2026-11-16: `RT-010..027`; ## Rules for contributors

- A new tenant-owned route family needs checks in this suite in the same work item: cross-tenant access by id (404), hidden-workspace behavior where it applies (404 vs 403), and a control that the legitimate request works.
- Change to authentication, sessions, tenant context, authorization or the Express/Fastify pipeline: `pnpm test:security` must pass before commit.
- Never point the suite at a real database; never weaken a check to make it pass.

## Alternatives considered

1. Keep scratch scripts outside the repo: not reproducible, not reviewable.
2. A full test framework with unit tests: broader than the owner approved and in conflict with the project constraints.
3. In-process `app.inject` tests: faster but Fastify-specific, so unusable as the gate for ADR-007.

## Consequences

### Positive
- The security-critical behavior is protected by a repeatable, transport-independent gate that runs in about 7 seconds.
- It is the acceptance gate for ADR-007.

### Negative / trade-offs
- Needs PostgreSQL server binaries on the machine (or a disposable database URL); no Docker.
- Depends on the seeded demo data (`demo.*@demo.example`); a change to the seed must keep the suite working.
- Covers only the scope above; it is not a general test suite.

## Security and operational impact

- Runs only against a disposable database it creates, or an explicit one whose name contains "test"; uses random credentials; leaves no files outside a temporary directory it deletes.
- Audit-log immutability means rows created by a run in an external test database stay there (use a throw-away database).
