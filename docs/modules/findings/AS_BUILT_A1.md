## 1. What was built

### 1.1 `packages/db/src/findings/` (exported from `@qmentisai/db`)

| File | What it holds |
|---|---|
| `transitions.js` | **`transitionFinding(tx, input)`**, the one function that changes `findings.status` (SPEC 6.2). Locks the row by tenant AND workspace AND id (`FOR UPDATE`), checks `expectedRev`, checks the shared table (`isTransitionAllowed`) AND that `reasonCode` belongs to that transition and that actor kind, sets `qm.finding_actor_type` for the transaction, updates the row (`rev + 1`), inserts the history row, the audit entry (`AUDIT_ACTION_BY_REASON`) and ONE `finding.status_changed` outbox hint, all in the caller's `tx`. Derives the SLA columns (SL-2): a stopped status clears `sla_due_at`; a reopen restarts the clock with the tenant's target (rows of `finding_sla_targets` over `SLA_DEFAULT_HOURS`); an approval to `approved` of a finding that had no clock re-arms it from first detection; `columns` always wins. `columns` is an allow-list of derived columns (a `status`, `rev` or identity key is a `TypeError`); a value may be a Prisma `{ increment }` for `reopenCount`. Errors: `FindingNotFoundError`, `FindingConflictError(reason)` (`stale_revision`, `transition_not_allowed`). |
| `errors.js` (new) | `FindingNotFoundError`, `FindingConflictError`. The API maps the first to the identical 404 and the second to `409 FINDING_STATE_CONFLICT` with `details.reason`. |
| `events.js` (new) | `FINDING_QUEUES`, `buildFindingMessage`, `enqueueFindingMessages`, `initiatorOf`. `@qmentisai/db` does not depend on `@qmentisai/contracts`, so the envelope is built with the same wire shape; `FNDA1-01`/`FNDDB-03` parse every message built here with the contracts' `parseMessage` and compare the queue names with `QUEUE_NAMES`. |
| `findings.js` | `createFindingsRepository({ db })`: `list`, `summary`, `getDetail`, `getForWrite`, `history`, `comments`, `similar`, `reviewQueue` (frozen names), plus the constant `MAX_FINDINGS_LIST_OFFSET` (10000). Raw SQL for the page and the counts (the one place the filters are built, shared by rows and total), Prisma for the rows. Details in 1.3. |
| `ingestion.js` | `createFindingsIngestionRepository({ db })`: `loadExecutionFacts`, `loadObservedItems`, `loadExisting`, `applyPlan` (frozen names), plus `lockAndCheck` and `recordFailure` (additive). Details in 1.2. |
| `agent-repository.js` | `createFindingsAgentRepository({ db })`: the five frozen methods. It imports NOTHING and issues only the statements the restricted role may run: SELECT on the view `fp_agent_findings` and on `tenant_llm_settings` and `finding_ai_advisories`, and ONE `INSERT ... ON CONFLICT DO NOTHING` into `finding_ai_advisories`. Secret findings are not in the view, so `getFindingForAdvisory` answers `null` for them; `readConsent` reports the second tier only when the first is on. |

### 1.2 Ingestion (`packages/db/src/findings/ingestion.js`, `apps/workers/src/findings/`)

- **Trigger (IN-1).** `apps/workers/src/execution/orchestrator.js` writes, in the SAME transaction as the `pipeline.execution.completed` event and ONLY inside `config.findings?.ingestionEnabled === true`, a second outbox row of the same envelope to the queue `findings` with the message id `execution-completed-findings-<executionId>`. The producer method `completedForFindings` was added to `apps/workers/src/execution/messages.js`. These two files are the only edits outside this part's directories (as `SPEC.md` 16.2 allows for the orchestrator).
- **Worker.** `apps/workers/src/findings/{index,main,handler}.js`, script `start:findings` / `dev:findings`, package export `./findings`, name in `WORKER_NAMES` and in the dev launcher. `start()` does nothing (and says so) unless `FINDINGS_INGESTION_ENABLED=true`. The consumer's ownership verifier (`executionInChain`) runs before the handler.
- **Handler.** The message is a wake-up. For each scan type (`sca`, `sast`, `secrets`) the handler: loads the execution facts by the WHOLE chain (tenant, workspace, repository, pipeline, execution id) from the database (a mismatch is dropped and logged, nothing is written); recomputes `resolutionEligible` from the rows (`isResolutionEligible` over the tasks and results; a disagreement with the event is logged and resolves nothing); reads the observed items (components, items without a detail row and unknown severities are left out; `preview` and `valueLength` are never read); then, in ONE transaction per `(execution, scan type)`: pipeline advisory lock (`findings:<tenant>:<pipeline>`), replay check (`finding_ingestions`), the existing findings of that pipeline and type, the pure `planIngestion`, `applyPlan`. A failing unit rolls back completely and is recorded as a `failed` ingestion row (best effort); the handler continues with the other types and rethrows at the end, so the consumer retries the message (finished units are replays). A unit's result is logged with the counters, `resolutionEligible`, `resolutionSkipped` by reason and the dropped counts (the metrics of SPEC 12).
- **`applyPlan` order.** creates (findings at rev 0, history row, evidence copy, `finding.created`, advisory job when `FINDINGS_AGENT_ENABLED` and `agentRunsOn`); observation updates (last seen, attributes, counters, evidence copy; the SLA is recomputed when the effective severity changes; `rev + 1` as the trigger demands); supersede of the pending review or exception of a finding that becomes fixed (`pending` to `superseded`); invalidation of an accepted risk whose severity rose (EX-5); verification records; every status change through `transitionFinding` (SM-14, SM-15, SM-16, SM-21) with `finding.verified` / `finding.reopened` events and a new advisory job on reopen; the pipeline markers (`finding_pipeline_state`, forward only); the `finding_ingestions` row.
- **Identity.** `computeFingerprint(item, pipelineId)` with the pipeline id from the verified execution row; the same item in two pipelines gives two findings with only the display-only `correlation_key` in common (`FND-S03`).
- **Fail closed.** No tracked ref, not the tracked ref, an untrusted fork, no result of the type and a deleted pipeline are recorded skips with their reason and create nothing. Incremental, partial, failed, cancelled, timed-out, fork, incomplete, truncated, tool-degraded, legacy (no coverage), targeted-scope, tool-not-run, gap-covered, disabled-type, older-than-watermark and event-database-disagreeing results never mark anything fixed (`FND-S06a`, 14 cases plus the control).
- **Free text.** Every text that reaches a column passes `clean()` (redacts a credential shape and caps the length); an excerpt, link or reference that still looks like a credential is not stored (the finding keeps its location). The scan tables already refuse credential shapes by CHECK; `FND-S04` proves the second defence by handing `applyPlan` observations that carry them.

### 1.3 Reads (`packages/db/src/findings/findings.js`, `apps/api/src/modules/findings/`)

**Routes (all `GET`, tenant audience, permission `finding.view` in the workspace, rate-limit profile `read`):**

| Route | Authorization scope | Notes |
|---|---|---|
| `/api/v1/findings?workspaceId=` | the workspace of the query, loaded by tenant and id | `workspaceId` REQUIRED; strict query (`listFindingsQuerySchema`); numbered (`page`, `pageSize` 25/50/100) or keyset (`cursor`, `limit` up to 100); neither given means keyset, first page, limit 25 |
| `/api/v1/findings/summary?workspaceId=` | same | `summaryDtoSchema` |
| `/api/v1/findings/{id}` | the finding's OWN workspace, the finding loaded by tenant and id | `findingDetailSchema`; header `ETag: W/"finding-<rev>"` |
| `/api/v1/findings/{id}/history?cursor&limit` | same | newest first, keyset only |
| `/api/v1/findings/{id}/comments?cursor&limit` | same | OLDEST first, keyset only |
| `/api/v1/findings/{id}/similar` | same | other pipelines of the same workspace, at most 20, links only |

`/findings/summary` is registered before `/findings/:id`. A workspace of another tenant, a hidden workspace, an unknown id and a finding of another tenant or hidden workspace are the identical 404; a visible workspace without `finding.view` is 403; a `tenantId` or any unlisted key in the query is 400.

**List behaviour.** Sorts `severity` (default, most severe first; the id tie-breaker ascending), `slaDueAt` (ascending, NULLs last), `firstDetectedAt` and `lastSeenAt` (newest first by default), `title`; `direction` flips the primary term. Filters: `view` (the four saved views), `severity`, `status` (csv), `scanType` (csv), `pipelineId`, `repositoryId`, `assignee` (`me`, `unassigned`, a user id), `sla` (csv of `on_track`, `due_soon`, `breached`, `none`), `aiSuggestion` (the latest `ok` advisory; `none` = no `ok` advisory), `q` (title, rule id, path: substring, case-insensitive, `%` and `_` literal). All filters AND together; tenant and workspace always come first. **Effective status:** an `accepted_risk` or `suppressed` finding whose `exception_expires_at` has passed is treated as `reopened` by every status predicate, by the DTOs and by the summary (EX-3), before the expiry job runs. Cursors are signed (`lib/keyset.js`) and bound to the endpoint, the tenant, the workspace, every filter, the sort and direction and the USER (so `assignee=me` and the assigned-to-me view cannot be replayed by another user). Date keys travel at microsecond precision. A numbered window is limited to `MAX_FINDINGS_LIST_OFFSET` (10000).

**DTOs.** The shapes are the frozen `findingListItemSchema`, `findingDetailSchema`, `historyEntrySchema`, `commentDtoSchema`, `similarFindingSchema`, `summaryDtoSchema` (`apps/api/src/modules/findings/mappers/index.js` builds them field by field; no Prisma model leaves the repository). Decisions where the specification left room: `sla.state` is derived at read time and is `not_applicable` outside the open statuses; `advisory.status` is `none` when there is no row, `ready` for `ok`, `consent_blocked`, `not_configured`, and `failed` for every other row status; `coverage.notScannedRecently` is true for an open finding not seen for 30 days (a recommendation, not a rule); `provenance.tools` lists only tools of the platform catalog; the commit-pinned `link` is re-validated (https, no userinfo, host in the closed table `github.com`, `gitlab.com`, `bitbucket.org`, the 40-hex commit of its structured `scmRef` inside the path) and is `null` otherwise; a secret finding's `evidence.snippet` is passed only when it contains the platform mask `[REDACTED`, else `null`. **`lifecycle.allowedActions`** is computed from the caller's permissions in the workspace and the state machine only; the own rules of an action (segregation of duties, assignee, requester) are NOT evaluated and are enforced by the write services of Parts B and C, which replace `computeAllowedActions` in the mapper (a clearly commented extension point) and add the `disabledReason` for them.

`getForWrite`, `reviewQueue` (and the service method `reviewQueue`) are implemented for Parts B and C; no route uses them yet. `findingScope` and `workspaceQueryScope` (`repositories/read-scopes.js`) are the scope resolvers Parts B, C and D reuse for their item and collection routes.

### 1.4 Seed (`packages/db/prisma/seed-findings.js`)

```
FINDINGS_SEED_ALLOWED=true pnpm --filter @qmentisai/db seed:findings -- --tenant <slug> [--workspace <id>] [--scale small|medium|large]
```

Refuses `NODE_ENV=production`, a missing `FINDINGS_SEED_ALLOWED=true`, an unknown tenant, workspace or scale, before writing anything; never prints a connection string, password or secret. `small` = 120, `medium` = 2,000, `large` = 100,000 findings (the first 3,000 carry a lifecycle; the rest are `new` and are written in batches of 500), plus three edge cases. Deterministic (a fixed generator seeded per index) and idempotent by fingerprint (a second run creates 0). It creates, when absent, seven demo users `seed-<role>@seed.example` (tenant members, no credentials), two repositories and four pipelines named `seed-*` (one deleted). Every finding carries the product's own fingerprint and correlation key; lifecycles go through `transitionFinding` (humans as the seeded users, the machine as `system:ingestion` / `system:expiry`), with real reviews, approvals (the approver is never the reviewer), exceptions, assignments, remediation and verification records and advisory rows (all three suggestions, `failed`, `consent_required`). Covered: all 12 statuses (an acceptance expiring in two days and one expired and reopened are always present), all severities, SCA (npm, PyPI, Go, Maven), SAST and secrets (the masked line only), SLA states on time, due soon and breached, the same vulnerability in two pipelines (indexes 30 to 44 repeat 0 to 14), a deleted pipeline, a Unicode path, the 1024-character path and a finding without evidence. The `findings:backfill` command is NOT built (see section 3).

## 3. Deviations from the specification and why

1. **`findings:backfill` is not built.** OD-7 says nothing backfills automatically and the command is optional; it needs the ingestion path with a "never resolves" mode, which is a small addition once the flag is in use. Open for the integrator.
2. **`large` seed carries a lifecycle for 3,000 findings only** (batched `new` rows for the rest) so a 100,000 run finishes in minutes; spec 9.4 describes every status at every scale.
3. **Watermark compared with the same execution (IN-6).** The markers are per pipeline but the units per scan type, so the first unit of an execution moves the watermark to that execution's start and the second would see "start <= watermark" and refuse to resolve. `loadExecutionFacts` therefore presents a watermark equal to this execution's own start as one millisecond earlier: only strictly older executions are stale. `evaluateCoverage` and `planIngestion` (frozen) are untouched. Found by the first run of `FND-S05b`.
4. **One `finding.status_changed` hint per transition and, additionally, the domain events `finding.verified`, `finding.reopened`, `finding.created` written by ingestion** (SPEC 9.1 names the producers this way). `FND-S14` ("each transition emits exactly one outbox row") is Part F's and must count `finding.status_changed` rows, not all `finding.*` rows.
5. **The `finding.advisory.requested` message id** is `finding-advisory-<findingId>-created` or `-r<rev>` (reopen), not `<inputHashShort>`: the input hash is the agent's, computed at advisory time; the agent deduplicates by `(finding, input hash)` anyway.
6. **`first_detected_at` is the execution's `started_at`** (not the ingestion time), so the SLA clock starts at detection even when ingestion lags; a missing commit sha is stored as 40 zeros (the columns are NOT NULL; an execution on a baseline branch always has one).
7. **Observation updates write no history row** (A0 deviation 3) but DO raise `rev` by one (the trigger demands it); a UI that holds an old `rev` therefore gets `stale_revision` after any recurrence, which is the intended optimistic-concurrency behaviour.
8. **`GET /findings/{id}/comments` is oldest first, history newest first** (SCREENS.md fixes the history order only).
9. **A0 check `FNDA0-15` was edited in one place:** it asserted that the Part A1 repositories "reject as not implemented"; for the factories owned by A1 it now only checks that the frozen method names exist (the parts still to come keep the assertion).
10. **`apps/api/scripts/snapshot-contract.js`** reads every `routes/*.routes.js` of a module, not only `routes/index.js` (the findings module splits its routes by part); without it `pnpm contract:snapshot` fails with "Cannot match these OpenAPI operations to a route source". The read routes call `inWorkspace(key, scope)` so the extractor records the permission. Parts B, C and D need the same extractor and will not need to touch it again.

## 4. Defects found in the frozen contract (reported, not edited)

1. **`FINDING_STATE_CONFLICT` has no HTTP status in `apps/api/src/errors/app-error.js` (`ERROR_HTTP_STATUS`).** The code exists in `@qmentisai/contracts`, but an `AppError` with it would answer `500`. Proposed change (one line, Part B before its first write route): `[ERROR_CODES.FINDING_STATE_CONFLICT]: 409,`. No A1 route raises it.
2. `FindingConflictError`/`FindingNotFoundError` live in the new `errors.js`; Parts B and C must reuse them (and `buildFindingMessage`) rather than define their own, or `export *` of `findings/index.js` would collide.
