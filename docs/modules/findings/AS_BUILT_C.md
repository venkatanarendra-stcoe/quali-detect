## 1. What was built

### 1.1 Routes (all tenant audience; every write takes `Idempotency-Key` and the `write` rate limit, reads the `read` limit)

Every item route loads the finding by TENANT and id and authorizes in ITS workspace (`findingScope`): a hidden workspace, another tenant's finding and an unknown id are one identical `404`; a visible finding without the key is `403`. A body never carries `tenantId`, `workspaceId`, `status`, `pipelineId` or a user id besides the assignee (the frozen schemas are strict). **A write answers with the finding detail DTO as the CALLER now sees it** (the E mock's shape, like Part B) with a new `ETag: W/"finding-<rev>"`; `POST assignments` answers `201`, the rest `200`.

| Method and path | Permission (route) | Request | Effect |
|---|---|---|---|
| `POST /findings/{id}/assignments` | `finding.assign` (finding's workspace) | `{ assigneeUserId, note?, expectedRev }` | SM-9 (`approved` to `assigned`), SM-17 (`reopened` to `assigned`) or the reassignment SM-10 (`assigned` or `in_remediation`, status unchanged). The assignee must be an active member of the tenant holding `finding.remediate` in the workspace (decided by the central engine, `authz.service.resolveFor`): `400 VALIDATION_FAILED / assignee_not_eligible` for a viewer, a user of another tenant, an inactive user and a stranger alike. `403` reasons: `FORBIDDEN / not_assignee` (a start or submit by someone who is not the assignee and does not hold `finding.assign`; same word as the E mock), `missing_permission`. `409 FINDING_STATE_CONFLICT` reasons: `stale_revision`, `transition_not_allowed` (including a reassignment to the person who already has it and a start or submit from a status the transition does not allow; the status is decided before the caller), `pipeline_deleted`. `CONFLICT / workspace_archived` for an archived workspace. `INVALID_CURSOR` for a board cursor of another column, filter set, workspace, tenant or user, or a tampered one.

### 1.2 The board (`services/board.js`, `repositories` of `@qmentisai/db` `assignments.board`)

One status per column (SPEC C-3). The query reuses the list's `buildWhere` (tenant AND workspace first, every filter narrows, a `pipelineId` of another workspace or tenant gives an empty column; an expired acceptance reads as `reopened`) with `sort: severity` (most severe first, the id ascending) and a signed keyset cursor bound to endpoint, tenant, workspace, caller, column and filters. "Verified fixed" shows the last 30 days (`verified_at`, a new `verifiedSince` filter in `buildWhere`). **The card** is the list item plus `canRemediate` (computed for the caller: `finding.remediate`, the card is `assigned` or `in_remediation` on a live pipeline, and it is theirs unless they also hold `finding.assign`) and, new by the owner decision of 2026-11-24 (SPEC 0.5 OD-10), `pullRequestUrl` and `ticketKey` of the latest submitted fix (optional, nullable; one extra query per page over `remediation_records`). `boardCardSchema` in `@qmentisai/shared` `schemas.js` is the only change to a frozen shared file (not exported: the export surface is unchanged).

### 1.3 SLA (`assignments.js`, `apps/workers/src/findings/sla.js`)

- **Settings.** `readSlaTargets` serves the tenant's rows over `SLA_DEFAULT_HOURS` with `isDefault`. `writeSlaTargets` replaces the rows (upsert the given severities, delete the others) and returns the changes; the service audits `tenant.findings_sla_changed` in the same transaction with the previous and new hours of what changed (numbers and enums only), and writes nothing and audits nothing when nothing changed. A change is **not retroactive**: a running clock keeps its due date; the targets apply when a clock starts again (`transitionFinding`'s reopen, the approval re-arm), which already reads `finding_sla_targets`. Proven per tenant by `FND-S14c`.
- **The sweep.** `findings.sla.sweep` (a platform job in the `findings` queue, one per five-minute bucket, enqueued by the scheduler **only while `FINDINGS_INGESTION_ENABLED=true`**, exactly like the expiry job): `createSlaSweepHandler` asks `assignments.dueForSweep(now, 200)` for open findings whose clock crossed due soon (the last quarter, the same arithmetic as `deriveSlaState`) or breached and are not yet notified in this cycle, and handles each in its OWN transaction with the row locked and the condition re-checked (`notifySla`): the marker column is set (`sla_due_soon_notified_at` or `sla_breach_notified_at`; a breach also marks due soon) and the event `finding.sla_due_soon` or `finding.sla_breached` is written to the outbox (the finding, workspace, severity and due date; initiator the system actor `findings-sla`; message id carries the due date). **Once per finding and cycle:** a marker older than `sla_started_at` belongs to an earlier cycle, so a reopening (which restarts the clock) notifies again without any column being reset; a second run, a concurrent instance and a later breach after the due-soon notice emit exactly one of each. At most 5 batches of 200 per tick; a failing item is logged (ids only) and does not stop the others. The sweep changes no status, assignee or history row; it raises `rev` by one (the update trigger demands it), like an ingestion observation.
- The handler is dispatched by a two-line edit of `handler.js` and the scheduler gained one tick (see 4).

### 1.4 Verification stays with ingestion (RM-2)

There is no route that verifies or reopens. `remediation.record` moves only to `in_remediation` and `fixed_pending_verification`; the claim sets `fix_claimed_at` and `absent_count = 0`, so A1's `planIngestion` verifies it on the next eligible full scan that does not contain it (`absent_count` reaches N) and reopens it on any detection with the `failed` outcome. `FND-S08e` proves it through the real handler (see 2). No change to ingestion.

### 1.5 The pending and stale advisory (the Part D-integration follow-up)

- **Pending** (`findings.js` `getDetail`, a new `hasPendingAdvisoryRequest`): a `finding.advisory.requested` outbox row for THIS tenant and finding, written within the last **5 minutes**, with no `finding_ai_advisories` row newer than it. Both producers write that row (A1 ingestion for created and reopened findings, D's manual request), so the outbox is the marker: **no new table, no migration**. An answered request leaves a newer advisory row; a request the agent drops (same input hash, secret or `info` finding) times out after the window. One read of the detail; **the list never reads the outbox** (`FND-S12d` counts the queries).
- `toAdvisoryDto(row, { pending })` now returns `{ status: "pending", stale: false }` whenever `pending` is true, even when an older advisory exists (SPEC: "pending = a request exists and no advisory row newer than it"). Consequence: for up to five minutes after a manual request that the agent turns into a duplicate (the same input hash within one clock hour, D-integration deviation 3), the card says "being prepared" instead of the still-valid old advice.
- **Stale is an APPROXIMATION.** The agent's input hash covers the provider kind, the egress level, the hardened excerpt and day counters that only the worker knows, so the API cannot recompute it, and the evidence copy is replaced on every observation. `isAdvisoryStale` therefore says: the latest advisory is `ok` and older than the evidence copy's capture (`finding_evidence.captured_at`, the start of the execution that last observed the finding) or older than `reopened_at`. It errs on the side of "ask again": every later scan that observes the finding marks the advice stale, whether or not the code changed. The request action's `advisoryPending` reason (Part B) now works because the DTO status is real.

## 3. Deviations from the specification and why

1. **`POST /findings/{id}/assignments` answers `201` and the other writes `200`**, all with the finding detail DTO (the E mock's shape, as Part B). 8.2 does not name the status.
2. **`not_assignee` is a `403` reason** (the E mock's word); `FINDING_FORBIDDEN_REASONS` of `@qmentisai/shared` lists only the first two of SPEC 8 (Part B already added `not_reviewer`, `not_requester`).
3. **The status is decided before the caller** for start and submit: a developer who starts an `approved` finding gets `409 transition_not_allowed`, not `403`.
4. **A reassignment to the same person is `409 transition_not_allowed`** (not in the spec): it changes nothing.
5. **`canRemediate` is stricter than the mock's** (`assignee || finding.assign`): it also needs `finding.remediate` and a card that can move (`assigned`, `in_remediation`, live pipeline). The E board only reads it for those two columns.
6. **A change of the SLA targets is not retroactive and does not recompute running clocks** (SL-1: "from the next recompute"): there is no recompute job. A clock keeps its due date until it restarts.
7. **The sweep raises `rev`** by one on each marked finding (the update trigger demands it for any `findings` update), without a history row (a status or assignee did not change). A UI holding the previous revision gets `stale_revision` after a notice, which is the intended optimistic-concurrency behaviour (as after a recurrence).
8. **`PUT /settings/findings-sla` has no `Idempotency-Key`** (SPEC FND-S11 says POST; the PUT is naturally idempotent: writing what is stored changes and audits nothing).
9. **Pending is capped at five minutes and `stale` is an approximation** (section 1.5).
10. **The 30-day window of "Verified fixed" uses `verified_at`**, which ingestion sets when it verifies (A1).
11. **The PR link has an extra service check** (`isStorablePullRequestUrl`: `https://host[/path]` with no whitespace, control character or `@` in the host part) so a link the database CHECK would refuse is a `400 invalid_pull_request_url`, not a `500`.
