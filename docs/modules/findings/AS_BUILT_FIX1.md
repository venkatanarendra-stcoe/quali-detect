## Item 2, D-F4 / S-1: the ETag covers the whole DTO as the caller sees it

- New `apps/api/src/modules/findings/mappers/etag.js`: `findingEtag(dto)` is `W/"finding-<rev>-<hash>"`, `<hash>` the first 32 hex characters of the SHA-256 of the canonical JSON (keys sorted at every depth) of the WHOLE DTO. The `finding-<rev>` prefix is kept (the body shows the same `rev`; nothing reads the prefix: the write routes take `expectedRev` in the body and `If-Match` is not read, UI never parses the tag). One function serves `GET /findings/{id}` and every write that returns the detail (review, approval, exception, remediation, assignment controllers), so a write answers with the tag the same caller's next read sends.
- `GET /findings/{id}` now answers `304` with the tag and no body on a matching `If-None-Match`, through `lib/conditional.js` (`isNotModified`), after authorization, scope and lookup (a 304 is never an oracle: the same plain 404/403 come first). `Cache-Control` is unchanged.
- The tag is computed over the caller's own DTO and sent only to that caller; it is a hash, holds no raw value, and two callers whose DTOs differ (allowed actions) get different tags. List and other routes set no ETag and were not touched.
- **UI:** `findingsApi.get` keeps `Cache-Control: no-cache` as belt and suspenders (one revalidation round trip, harmless); only its comment was updated (`apps/tenant-web/src/features/findings/services/findings-service.js`).
- **Checks:** new `FNDFX-01` (`findings-fix1-checks.js`, part key `FX`, count 1): identical reads give an equal tag and a matching `If-None-Match` an empty 304, a stale validator (the old rev-only tag) a 200; a second advisory row changes the tag with `rev` unchanged; the SLA state moving through the clock alone (due soon, then breached, no write between) changes it; the same user with other permissions (viewer, analyst) changes it and back again restores it; two callers with different allowed actions get different tags, each equal to the hash of its own DTO, and one caller's tag never validates the other's read; the tag shape is `W/"finding-<rev>-<32 hex>"` without the id, title, path or rule id; a claim answers with the tag of the next read. The two older assertions that pinned `W/"finding-<rev>"` on write responses (the assignment check of part C and the approval check of part B) now assert the new derivation (prefix with the stored revision and equal to `findingEtag` of the returned DTO).
- **Mutation check by hand:** the ETag was reduced to `W/"finding-<rev>"` once: `FNDFX-01` failed on the shape, the stale validator, the advisory, SLA and permission moves and the two-caller cases, and the older `FND-S07c` and `FND-S08c` failed too; restored.
