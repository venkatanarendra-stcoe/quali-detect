## 2. Contracts: `packages/contracts`

- **Queue:** `QUEUE_NAMES.REPORTING = "reporting"`; the broker topology is derived from the catalogue, so the main queue, the retry tiers and the dead-letter queue exist with no change to `packages/infra`.
- **Message types** (job, tenant scope, `schemaVersion` 1, `.strict()`): `reporting.rollup.requested` `{ tenantId, mode: incremental | close | backfill, day?, from?, to?, reason? }` (close needs `day`; backfill needs `from` and `to`, at most 800 days, no `day`; the others take no range; days are real calendar days) and `reporting.export.requested` `{ reportId }`. The payload `tenantId` must equal the envelope's (the handler checks it); `reason` (`scheduled`, `first_enablement`, `timezone_changed`, `repair`) is informational and is the one field added to the SPEC shape. The payload schemas live in `message-types.js` (the catalogue), not in `@qmentisai/shared`: `contracts` has no dependency on `shared`.
- **Error codes** (stable) and HTTP status (`apps/api/src/errors/app-error.js`): `REPORT_PERIOD_INVALID` 400, `REPORT_PERIOD_TOO_LONG` 400, `REPORT_AS_OF_UNAVAILABLE` 409, `REPORT_TOO_LARGE` 422, `REPORT_LIMIT_REACHED` 429, `REPORT_NOT_READY` 409, `REPORT_EXPIRED` 410, `REPORT_TEMPLATE_UNKNOWN` 400.

## 3. Database: ONE migration `20261126100000_reporting_core` and `packages/db/prisma/schema/reporting.prisma`

- **Tables (7):** `report_daily_findings`, `report_daily_executions`, `report_daily_decisions`, `report_daily_sbom` (primary key `(tenant_id, pipeline_id, day[, scan_type[, severity]])`, composite foreign key over `(tenant_id, workspace_id, repository_id, pipeline_id)` to `pipelines` and a tenant foreign key, both `ON DELETE CASCADE`, indexes `(tenant_id, workspace_id, day)` and `(tenant_id, pipeline_id, day)`, sparse rows, CHECKs for non-negative counters and for `open = backlog + work in progress`), `report_rollup_runs` (key `(tenant_id, id)`, unique `(tenant_id, day, mode, started_at)`, extra `range_to` and `time_zone` columns), `report_exports` (key `(tenant_id, id)`, composite workspace foreign key, CHECKs for the status vocabulary, the file facts of a ready report, `params` at most 2048 bytes and `object_key = reports/<tenant>/<id>.<format>`), `tenant_reporting_settings`.
- **Tenant time zone:** the SPEC names `tenant_settings.reporting_timezone`, but the product has no `tenant_settings` table (the settings are one table per module: `tenant_llm_settings`, `tenant_integration_settings`). The column is `tenant_reporting_settings.reporting_timezone` (one row per tenant, no row means `UTC`, CHECK non-empty, at most 64 characters, a name made of letters, digits, `_`, `+`, `-`, `/`); the IANA name is validated in code (`isValidTimeZone`).
- **Views (7, the six of SPEC 8.1 plus one):** `report_findings_v`, `report_status_events_v`, `report_decisions_v` (review decisions AND exception outcomes in one timeline: the as-of severity reconstruction needs both), `report_advisories_v`, `report_executions_v`, `report_sbom_latest_v`, and **`report_tenant_settings_v`** (tenant id, status and time zone: the worker has no other way to learn the zone). They run with the owner's rights; the roles need no source grant. Beyond the SPEC list they expose the repository, pipeline and assignee DISPLAY names (the exports and breakdowns need them). Never: evidence (snippet, `scm_ref`, url), rationale, comment body, advisory reasoning (nor its input hash or usage), exception justification and controls, status-history note, e-mail, fingerprint; the cross-pipeline key is NULL for a secret finding.
- **Roles:** `qm_reporting_ro` (SELECT on the 7 views and 6 `report_*` tables, nothing else; `default_transaction_read_only`, `statement_timeout 5s`, `idle_in_transaction_session_timeout 10s` as role settings) and `qm_reporting` (the same SELECT plus INSERT and UPDATE on the 6 `report_*` tables; no DELETE, no TRUNCATE, nothing on any source table or `tenant_llm_settings`). Both NOLOGIN groups created by the migration when its user may create roles (otherwise a NOTICE and the provisioning script does it). Because the roles have no DELETE, two `SECURITY DEFINER` functions (execute for `qm_reporting` only) do the rebuild and the retention: `qm_reporting_clear_range(tenant, from, to)` and `qm_reporting_purge(rollup_before, runs_before, exports_before, limit)`.
- **Provisioning:** `pnpm --filter @qmentisai/db provision:reporting-logins` (`REPORTING_DB_PASSWORD` and `REPORTING_RO_DB_PASSWORD`, each 16 characters or more, from the environment; login names `qm_reporting_login` and `qm_reporting_ro_login`; idempotent; never prints a password). Role settings do not pass from a group to a member, so the script also sets the read-only default and the timeout on the read LOGIN role.
- **Frozen repository surface** (`packages/db/src/reporting/index.js`; the parts fill `rollup/`, `read/` and `exports/` and never edit it):
  - `createReportingRollupRepository({ db })` (worker role; Part A): `getTenantSettings`, `listActiveTenants`, `listPipelineChains`, `earliestHistoryAt`, `startRun`, `finishRun`, `findLatestRun`, `listRuns`, `computeFindingsStateAsOf`, `computeFindingsFlow`, `computeExecutionsDays`, `computeDecisionsDays`, `computeSbomDays`, `upsertFindingsDays`, `upsertExecutionsDays`, `upsertDecisionsDays`, `upsertSbomDays`, `clearRange`, `purgeExpired`.
  - `createReportingReadRepository({ db })` (read role; Part B): `getTenantSettings`, `getRollupFreshness`, `getPosture`, `getPostureAsOf`, `getTrends`, `getRemediation`, `getSla`, `getAging`, `getScanActivity`, `getCoverage`, `getSbom`, `getQuality`, `getBreakdown`, `getTopRisk`, `getWorkload`, `getOverview`.
  - `createReportingExportsRepository({ db })` (the API's normal client; Part C): `createExport`, `countActiveExports`, `countExportsByUserSince`, `getExport`, `listExports`, `softDeleteExport`.
  - `createReportingExportWorkerRepository({ db })` (worker role; Part C): `claimExport`, `getExportForWorker`, `countExportRows`, `readExportPage`, `completeExport`, `failExport`, `expireExports`.

## 4. Flags and wiring

- `REPORTING_ENABLED` (default `false`) in the API and the worker configuration; `REPORTING_RO_DATABASE_URL` (API; required in production while on, otherwise the shared pool with a warning), `REPORTING_DATABASE_URL` (worker; the same rule), `REPORTING_ROLLUP_RETENTION_MONTHS` (25, worker), `REPORTING_EXPORT_RETENTION_DAYS` (30). `.env.example` lines in both apps, no secret.
- **Worker `reporting`** (`apps/workers/src/reporting/`): `main.js` and `index.js` start a consumer on the `reporting` queue only when the flag is `true`; `dispatch.js` and `handlers.js` (Part A0's, never edited by a part) route by message type; Part A fills `rollup/index.js` (`createRollupHandler`, `startRollupTick`), Part C fills `export/index.js` (`createExportHandler`). A factory that returns null means "not built yet": the message is dead-lettered (non-retryable), not acknowledged and lost. The dev launcher accepts `WORKERS=...,reporting`; `package.json` has `start:reporting`, `dev:reporting` and the `./reporting` export. **`pdfkit` 0.21.0** (MIT, pure JavaScript) is a dependency of `apps/workers` only.
- **API module `reporting`** (`apps/api/src/modules/reporting/`): registered in `modules/index.js`; `routes/index.js` mounts `routes/read.routes.js` (Part B) and `routes/export.routes.js` (Part C), both empty. The route deps carry `readDb()`, a lazy separate pool of the `qm_reporting_ro` login (`read-client.js`; created on first call, so with the flag off nothing connects). **Integration note for the lead:** `disconnectReportingReadClient()` is exported and must be called by the application's close hook (`apps/api/src/app.js`) once Part B uses the pool.

## 6. Decisions and deviations

1. **Tenant time zone table** instead of `tenant_settings.reporting_timezone` (no such table; the pattern is one settings table per module). Section 3.
2. **Seventh view** `report_tenant_settings_v`, names in the views, and `report_decisions_v` as a review and exception timeline. Section 3.
3. **Two functions** for clearing a day range and for retention, because the roles may not DELETE. Section 3.
4. **Message payload schemas** live in `@qmentisai/contracts`, not in `@qmentisai/shared` (no dependency edge); `reason` added to the rollup payload. Section 2.
5. **`REPORT_TOO_LARGE` is 422**, `REPORT_AS_OF_UNAVAILABLE` 409 (SPEC 9 names no status). Section 2.
6. **`report_rollup_runs.range_to` and `time_zone`** columns added so a backfill is resumable and a zone change is visible in the run.
7. **Empty suite part files** for A, B, C and E are created here (the aggregate imports them); the parts own them.
8. **Lockfile:** adding `pdfkit` re-resolved the optional `@types/node` peer of the `vite` entries (the vite and tailwind entries gained `@types/node@26.6.6` in their peer suffix); no version changed.
9. `report_sbom_latest_v` names its ids `sbom_execution_id` and `sbom_result_id` (not `execution_id`, `scan_result_id`): the Executions check `EXECDB-026` treats every column of that name in the schema as "execution-owned data" and would demand the view in its table enumeration (a purgeable row the reporting data deliberately does not pin).
10. The `docs/api` snapshots are NOT regenerated here (no route was added); the lead regenerates them after integration.
