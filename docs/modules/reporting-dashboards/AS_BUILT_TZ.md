## 1. Routes

| Route | Permission (tenant scope) | Rate limit | Idempotency-Key | Notes |
|---|---|---|---|---|
| `GET /api/v1/reporting/settings` | `tenant_settings.view` | `read` | no | the zone, who and when, `recomputing` |
| `PUT /api/v1/reporting/settings` | `tenant_settings.manage` | `write` | accepted (optional) | body `{ reportingTimezone }`, strict |

**Permission keys.** The brief said `tenant_settings.update`; the catalogue has **`tenant_settings.manage`** (`packages/shared/src/permissions.js`; `PUT /settings/ai` and `PUT /settings/findings-sla` use it), so the PUT uses `manage`. No new key, no role change (only the Administrator holds either key). A holder of neither gets 403 (a tenant key hides no resource, so there is no 404 for "another tenant": the tenant comes from the session, and `tenantId` in the body or the query is a 400). With `REPORTING_ENABLED` not true both routes answer the identical 404 `RESOURCE_NOT_FOUND` of every reporting route (the gate runs before authorization, after validation, like `POST /reporting/reports`).

**Body validation** (`updateReportingSettingsBodySchema`, `@qmentisai/shared`, file `reporting-settings.js`): a string of 1 to 64 characters that is a **canonical name of the runtime**: `Intl.supportedValuesOf("timeZone")` plus `UTC`, and formattable by `isValidTimeZone`. Everything else is `400 VALIDATION_FAILED`: unknown names, non-strings, over-long values, blanks around a name, wrong case (`utc`, `Europe/berlin`), `Etc/*`, legacy aliases the runtime does not list (`US/Pacific`, and `Asia/Kolkata` while the ICU of the runtime lists `Asia/Calcutta`), offsets, path tricks, extra keys. Decision: the tenant app offers exactly the list a browser reports, so the API refuses every other spelling and a stored zone is always one stable name. Consequence: the list is the runtime's; a name a newer browser lists and the API's Node does not is a 400 (the UI shows the server's message).

**DTO** (`reportingSettingsDtoSchema`): `{ reportingTimezone, updatedAt | null, updatedBy: { displayName } | null, recomputing }`. No row means `UTC`, `updatedAt` null. `updatedBy` is the display name of a member of the same tenant, never an id or an e-mail.

**`recomputing` (what was chosen, kept simple).** True when ALL of: the row was written through this route (`updated_by_user_id` set), it was written less than 24 hours ago, and no **succeeded `backfill` run of the tenant in the CURRENT zone, started at or after the change, whose `range_to` reaches the day of the change** exists in `report_rollup_runs`. The last batch of the rebuild ends at `to` = the day of the change, so its succeeded run ends the state. It means "a rebuild was requested and has not shown a finished run"; it cannot tell a queued message from a running one, and after 24 hours it stops claiming (a worker that is off, or a dead letter, does not keep the screen "Recomputing" forever). Honest limits: any other succeeded backfill of that zone started after the change (for example a repair) also ends it; a rebuild that fails and is retried keeps it true.

## 2. PUT behaviour (one database transaction)

Under a per-tenant advisory lock (`pg_advisory_xact_lock`, so two requests cannot both read the old zone): read the current zone (`UTC` when no row). **Same zone: no-op** (200 with the current DTO; no row is created for `UTC` on a tenant without one; no audit entry, no message, `updatedAt` unchanged, no cache bump). **A real change** writes, in the SAME transaction: (1) the `tenant_reporting_settings` upsert (`updated_by_user_id`, `updated_at`); (2) the audit entry `tenant.reporting_timezone_changed` (target `tenant_reporting_settings`, metadata `{ previous, new }` and nothing else; the actor, correlation id and IP from the session); (3) one outbox message on the `reporting` queue. A failing audit write or a failing enqueue rolls everything back (proved).

**The message.** `reporting.rollup.requested`, `mode: "backfill"`, `reason: "timezone_changed"`, `from` = the day of the tenant's earliest `finding_status_history` row in the NEW zone (capped at `min(rollupRetentionMonths * 31, 790)` days before today, the 25-month retention; with no history, today), `to` = today in the NEW zone (the cap respects the contract's 800-day limit). `initiator` is the user; the tenant is the session's.

**The message id rule.** `reporting-rollup-<tenantId>-tz-<zone, every character outside A-Za-z0-9._- replaced by "-">-<16 hex>`. The last part is the first 16 hex characters of `sha256("<tenantId>:<Idempotency-Key>")` when the request has a valid key, otherwise 16 random hex characters. There is **no hour or day bucket**, so two real changes inside one hour queue two messages (the hour-bucket ids of the tick and the operator script would have collapsed them), and a replay of the same key yields the same id (the outbox is unique per message id and queue). A replay normally never reaches the handler (the route kit's idempotency middleware answers the stored response with `Idempotent-Replayed`); the derived id is the second line of defence. A client without a key that retries a request that succeeded finds the zone already set and gets the no-op.

**Cache epoch.** After the commit the service calls `bumpTenantReportingEpochs` (new, in `read-cache.js`), which bumps through the existing `createReportingEpochBumper` the epoch of every workspace of the tenant and of the tenant-wide overview, so cached trends of the old zone are never served (the keys stay built in one place). It runs after the commit so a reader cannot re-cache the old zone between the bump and the commit; if the process dies in between, or Redis is down, the entries expire by TTL (300 s for rollup reads, 30 s for live ones) and the change itself never fails.

The rebuild runs in the reporting worker exactly as before (`runBackfill` with `reason: "timezone_changed"` clears the range, voids the run coverage and recomputes; the severity and backlog state series are forward-only and show unknown from the change, `AS_BUILT_A.md`, `AS_BUILT_AM.md`).
